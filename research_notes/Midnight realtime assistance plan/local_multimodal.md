## What models and hardware do we actually have?

### Takeaway

The machine already has useful local assets: Whisper-base, EmbeddingGemma 2 in two older/newer forms, and both Gemma 4 E2B and E4B quantized executors. They live across the current app and the sibling runtime project, so reuse requires an explicit runtime/component integration and migration; the current app does not already have a functioning native audio/video executor.

### Inferences

- First implementation task is model inventory reconciliation, not shopping for more base models. Keep old caches intact during migration. Import/reuse exact signed GGUF components where hashes verify, supervise them through a shared headless runtime API, and avoid pretending the old Python prepared manifest is current ONNX readiness.
- Choose one production embedding backend and fingerprint each index by model revision, quantization, dimensions and preprocessing. Switching Python/ONNX/GGUF must regenerate or validate vectors before atomically switching the active generation; byte-compatible weights do not imply vector-compatible indexes.
- Use E2B for short command routing and structured small patches first. Try existing E4B for paragraph revision where quality gains justify latency, with explicit fallback to E2B or an authorized cloud route. Local/offline modes must never silently send work to cloud.

### Gaps

- Files were size-checked, not freshly hashed; current load readiness and memory pressure under Word workload are unmeasured.
- No comprehensive scan of all user storage was made. Inventory is restricted to repository-derived app/runtime/cache paths, so unrelated models elsewhere are unknown.
- The observed installed old search runtime may differ from the running packaged app version. Diagnose before migration; do not rewrite or delete old assets in place.

## Do these models actually hear, see video, and stream natively?

### Takeaway

Gemma 4 E2B/E4B can receive audio and image/frame sequences at the model-family level, and the pinned llama.cpp build includes corresponding encoders and transport. The app currently does not wire those capabilities: its Gemma executor has no projector and its direct adapter drops images. Native model input, clip-based perception, token streaming, and a persistent realtime AV model are separate capabilities.

### Inferences

- Product language should distinguish `speech transcription`, `raw audio clip input`, `non-speech sound matching`, `image understanding`, `ordered frame clip understanding`, and `persistent streaming AV`. Report only tested capabilities as ready.
- Keep existing Whisper as the dependable command transcription baseline. An E2B native-audio spike can receive a bounded utterance directly and return text/intent, but do not remove the ASR fallback until code-switched English/Malay, noise, numbers, dates, and exact editing targets pass tests.
- First native multimodal increment needs the matching E2B projector plus typed content transport and readiness tests, rather than a new generative base model. Add it as a signed optional component with pairing information, hash, clip limits and test status. Delay even this ~986MB download until implementation work and a bounded acceptance experiment are authorized.
- Preserve audio waveform and its timestamps briefly when the user requests acoustic interpretation; a transcript irreversibly discards acoustic information. Treat prosody/non-speech explanation as an experiment, never a shipping guarantee based on ASR alone.

### Gaps

- Missing E2B/E4B projectors mean exact installed native image/audio output and ordered-frame quality are untested.
- No evidence these models have a persistent efficient audio/video session with arbitrary input streaming, state reuse or full-duplex speech output. Gemma outputs text; speech synthesis would be a separate future capability.
- Combined audio+video alignment must be tested; accepting both parts does not establish timestamp synchronization or correct causal reasoning.

## How should realtime assistance run efficiently on this hardware?

### Takeaway

Use an event-driven local perception and action system with explicit invocation first, bounded clips/crops and one expensive model job at a time. Realtime should mean immediate target capture/feedback, timely cancellation, and a small preview within seconds; it cannot honestly promise continuous heavy native AV reasoning on this machine based on the available evidence.

### Cited Findings

- Existing current-app embedding calls are serialized, embedding inference caps CPU threads at4, and the worker unloads after60s idle. Speech unloads after120s but has no explicit worker thread cap, supports max5min recordings, and returns final transcription. — [embedding worker](../../src/search/embed-worker.mjs), [embedding lifecycle](../../src/search/runtime.mjs), [voice lifecycle](../../src/voice/runtime.mjs).
- The sibling Gemma executor defaults to8192 context,7 threads on this8-logical-core CPU,1024 output tokens and thinking disabled for fast tool steps. These defaults are suitable starting code, but reserving only one logical thread is not a measured background-work policy. — executor (external checkout: `../midnight/packages/runtime-host/src/local-agent.ts`; relative to the repository root, not included here).
- b11560 exposes separate generation/prefill threads, context/KV types, low-priority/poll controls, multimodal token budgets, residency/sleep and monitoring controls. These offer implementation controls; tuning results must be measured by workload. — [Server options](https://raw.githubusercontent.com/ggml-org/llama.cpp/b11560/tools/server/README.md).
- A small optional speech-activity component is possible with Silero VAD's ONNX model. Its publisher supplies a realtime example and ONNX CPU usage, but its published latency does not measure this laptop/Node integration. Wake word recognition is a separate optional detector, with additional model/license review required. — [Silero VAD](https://github.com/snakers4/silero-vad), [openWakeWord](https://github.com/dscripka/openWakeWord).

### Inferences

Recommended operating design, **not implemented or measured**:

1. **Invocation first.** Global hotkey captures selected object/paragraph plus active app identity; push-to-talk captures only while held. Show a small target outline/listening indicator within100ms. An explicit request freezes a revision-tagged context capsule so later focus changes cannot retarget the edit. Ambient mode is off by default and separately opt-in per app/device.
2. **Audio budget.** Use audio worklet PCM chunks rather than waiting for one long MediaRecorder blob; bounded mono16kHz ring buffer, initially2s preroll and max15s utterance/30s hard clip. VAD only during held capture or opted-in ambient mode. Silence/endpoint handling is lightweight; explicit release can finalize. Partial transcription is display-only until the final intent is stable. Under overload, never silently drop an explicit utterance; backpressure capture or explain retry. Replace the5min product command path with small-turn defaults while retaining dictation as a separate mode.
3. **Visual budget.** Read app object APIs/accessibility and selection events first. Capture a selected object/region only when structure is insufficient. Start with one crop; use2–4 timestamped frames over a short interval only for a temporal task. Coalesce event bursts, drop obsolete unprocessed background frames, and keep a single freshest frame per target. Use70/140-token coarse frames,280-token ordinary crops,560/1120 only when small text actually needs it; benchmark these budgets instead of promising native full-screen30fps.
4. **Context budget.** Paragraph command: selected paragraph,1 adjacent paragraph on either side at most, style constraints and requested transformation, typically≤1500–2500 input tokens. Chart command: selected chart ID/type, data and category/series metadata, current revision and requested type, typically≤2000 tokens. No full-document default. A bounded timestamped event memory stores identity/revision and short observations; raw audio/frame buffers expire quickly. Any extra context request must be relevant and scoped.
5. **Router.** Deterministic direct operation where intent and target are known; otherwise E2B short-intent/structured-patch inference. Whisper handles speech. EmbeddingGemma handles retrieval/deduplication only when needed. Gemma E2B+projector handles a crop/short audio clip after its capability fixture gates pass. Existing E4B is an on-demand quality tier for paragraph wording. Cloud is an explicitly allowed policy route; local/offline never escalates automatically.
6. **Capability record.** Store model ID+revision+quant, runtime build/backend, projector hash, loaded status, supported tested modalities, max clip/context, schema/tool accuracy, cold/warm p50/p95, and measured RSS. Route from this record rather than one `vision` checkbox. Missing/unverified capability produces the known pipeline fallback (ASR+text, accessibility/OCR+text), not a fabricated claim of native hearing/seeing.
7. **Scheduler.** One active heavyweight inference/prefill across ASR, executor and multimodal embedding; pause background file indexing for an explicit command. Start2 threads/background and3–4 threads/invoked as candidates on this4-core CPU, with generation/prefill separated and OS process priority below normal for background. Leave tiny capture/VAD/UI tasks independently responsive. Hard cap queue depths and deadlines; cancellation propagates to server/worker. An explicit request takes precedence over ambient suggestion/indexing and over AI self-improvement builds.
8. **Residency and memory.** Keep E2B warm for a short opted-in work session if RAM permits; unload after2–5min idle/battery constraints, keep E4B cold by default, and do not keep both executors plus all modality encoders resident. Text-only embedding should omit unused encoders where the selected runtime supports it. Start a soft3GiB foreground-app reserve and report RSS/commit/paging; refuse new heavy jobs when reserve falls below target. Quantized file bytes are not process memory estimates. Bound context/KV initially4k–8k, max256 tokens for routing and≤512 tokens for narrow rewrite, with direct deterministic application avoiding extra confirmation/report model turns.
9. **Battery and thermal policy.** Hotkey/push-to-talk still work on battery; indexing/ambient interpretation waits for idle and power unless opted in. Stop observation on screen lock/sleep, pause immediately on permission revocation, and suppress irrelevant ambient suggestions while typing. Test typing latency, fan/CPU activity, battery delta and dropped input alongside model latency.
10. **Recovery.** Retain explicit-vs-ambient event identity, target revision and retry provenance. Never replay a captured audio command after resume/crash as a fresh authorization. Native modality failure falls back within the existing explicit request while respecting its target/scope and local privacy policy.

Proposed SLOs are **design/acceptance targets**, not claims of achieved speed:

| Path | Candidate target | Audit evidence / limitation |
|---|---|---|
| Hotkey/listening/target feedback | p95≤100ms | Deterministic UI/capture metadata; must be tested with Word active |
| Escape/stop visible response | p95≤100ms; application mutation fenced immediately | Model cancellation can finish later; fence input instantly |
| Selected object metadata/crop | p95≤300ms | App/API availability unknown; no fresh capture benchmark |
| Warm E2B small text intent | p95≤5s | Existing small fixture p95≈4.4s with aggressive7-thread configuration; reserve-aware profile may be slower |
| Simple deterministic chart change after intent | p95≤1s API apply+verify | App integration gate; model turns excluded; no chart automation benchmark |
| Selected paragraph preview, warmed model | p95≤10s initially | Existing E4B small-tool p95≈9.7s; actual text length/edit quality unmeasured |
| Push-to-talk final intent after release | p95≤5s aspirational | Whisper/native clip latency unmeasured; report achieved values and tune before promising |
| Idle always-available footprint | no heavyweight inference; background CPU average≤1%, idle extra RSS≤250MiB target | Requires measured headless/Electron split; not achieved claim |
| Warm-session memory | one executor; reserve≥3GiB for foreground workloads | Peak RSS/KV/projector and paging under actual Word workload unknown |

Minimal acceptance sequence: (a) discover and verify cached components and legacy manifest migration; (b) test E2B/E4B selected-paragraph quality and current CPU profiles using synthetic fixtures; (c) implement selected-object API path and prove only its revision changes; (d) add optional matching E2B projector and synthetic image/audio/ordered-frame tests on b11560; (e) implement bounded push-to-talk, ASR fallback and cancellation; (f) measure30–60min background/Word sessions on battery and AC; (g) only then expose per-app opt-in ambient capture and stable partial-intent handling. Every measurement records cold/warm state, backend, thread count, context/output/clip budget, foreground workload and power state.

### Gaps

- Native audio/image latency, actual paragraph rewrite duration/quality, revision-safe Word chart edits, thermal/battery overhead, projector RSS and residual cancellation compute are unmeasured.
- Existing evaluations are small and optimistic for resource budgeting. Realtime acceptance must include active Word, multiple open apps, user typing, focus drift, overlapping commands, noise, code switching and sleep/lock.
- If measured latency misses the experience target, reduce context/output, use deterministic app operations and warm E2B before considering another base model. Any additional model/runtime should follow a documented failed gate; no new large model purchase or download is presently justified.
