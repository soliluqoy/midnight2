# Pi and Pi Durable capabilities for Midnight self improvement

> **Historical upstream research — checked 13 October 2026.** Upstream versions and API findings retain their original research date; they have not been requalified here. The separate Midnight builder described as proposed below now exists for chart/color plugins and development app-source proposals. See the [reconciled architecture](../../reports/Midnight%20self%20improvement%20architecture.md) and [current implementation status](../../docs/realtime-implementation.md). Repository links navigate to current files; obsolete source line numbers have been removed.

## What does Pi provide for prompting an app to improve itself?

### Takeaway

Pi supplies a malleable coding agent and integration APIs. Its extension system makes the agent changeable; Midnight still needs its own application plugin contract, build/test pipeline, preview, activation, update distribution, and recovery path. These are separate concerns. [Pi overview](https://pi.dev/docs/latest), [Extensions](https://pi.dev/docs/latest/extensions)

### Cited Findings

- Research freshness: checked 2026-10-13. The official changelog lists Pi **1.2.0**, released 2026-10-12. Tagged sources below use `v1.2.0` wherever possible; `latest` documentation is a moving reference. [Official changelog](https://pi.dev/changelog)
- Pi's stated philosophy is to keep the harness minimal and adopt proven capabilities. The official 1.0 announcement demonstrates Pi writing a virtual-model extension for itself, then reloading and selecting the new model. This is evidence of code generation plus extension loading, not a guarantee that every generated change works or an app deployment mechanism. [Pi 1.0 announcement, 2026-10-01](https://earendil.com/posts/pi-1-0/)
- The extensibility mechanisms have distinct roles: prompt templates reuse prompts; skills provide task-specific instructions and supporting files; themes change terminal appearance; TypeScript extensions add executable tools, commands, event handlers, providers, state and terminal UI. [Overview](https://pi.dev/docs/latest), [Skills](https://pi.dev/docs/latest/skills), [Extensions](https://pi.dev/docs/latest/extensions)
- Skills are directories with `SKILL.md`, optionally scripts, references and assets. Pi initially advertises their name/description/path; the model reads full instructions when relevant. `/skill:name` forces invocation and `/reload` picks up skill edits. A skill can instruct the model to execute bundled scripts, so Markdown packaging alone does not imply harmless behavior. [Skills](https://pi.dev/docs/latest/skills)
- Coding-agent extensions export a default factory receiving `ExtensionAPI`; examples include `pi.registerTool()`, `pi.registerCommand()`, and `pi.on()`. Pi loads TypeScript using `jiti`. Reload replaces the extension runtime; old runtime state must not be reused. Long-lived resources start with the session or a tool/command and close through an idempotent `session_shutdown`. [Extensions](https://pi.dev/docs/latest/extensions)
- Extensions execute within the Pi process and can inspect prompts, files, credentials and history. Pi's working directory is a discovery/default-path setting, not filesystem confinement. Project trust gates resource loading, not tool authority, prompt injection or OS isolation. A separate process still inherits its OS user's permissions; a whole-process sandbox/container/VM imposes a stronger boundary than routing only built-in tools elsewhere. [Security](https://pi.dev/docs/latest/security)
- Pi packages distribute extensions, skills, prompt templates and themes through npm, git or local directories. They use conventional directories or a `pi` key in `package.json`, carry runtime dependencies, and support pinned npm versions/git tags/commits. `pi install`, `pi remove`, `pi list` and `pi update --extensions` manage package declarations/installations. This manifest does not describe Midnight React views, navigation slots, migrations or Electron permissions. [Packages](https://pi.dev/docs/latest/packages)
- Pi terminal extension renderers and `ctx.ui` are for Pi's TUI. RPC forwards supported dialogs/notifications but does not forward custom terminal components; JSON/print modes lack UI. These APIs do not mount views in Midnight's renderer. [Extensions](https://pi.dev/docs/latest/extensions)
- Both packages are MIT licensed. Redistribution and modification are permitted with the license/copyright notice retained. This covers upstream Pi code; third-party packages and assets need their own license review. [Upstream license](https://raw.githubusercontent.com/earendil-works/pi/v1.2.0/LICENSE), [Pi announcement](https://earendil.com/posts/pi-1-0/)

### Inferences

- Use Pi's principle of a small understandable substrate, and distinguish four customization levels: data/settings; skills/prompts; capability/UI plugins; core source changes. Each level needs a different activation and verification path. This is a Midnight design recommendation inferred from Pi's separate mechanisms. [Overview](https://pi.dev/docs/latest)
- A Midnight plugin can expose its agent tools to Pi through an adapter, and expose its UI through Midnight's own slots. A Pi extension may be one implementation resource inside that plugin, but should not become the app plugin API itself. Pi's extension UI/modes are a different host interface. [Extensions](https://pi.dev/docs/latest/extensions), [Packages](https://pi.dev/docs/latest/packages)
- Per-installation customization and official shared changes can use the same builder workflow but different destinations: a versioned local overlay/plugin versus the official source/release pipeline. Agent code generation cannot replace this distinction. [Packages](https://pi.dev/docs/latest/packages), [Security](https://pi.dev/docs/latest/security)

### Gaps

- No upstream mechanism found that validates generated Midnight UI, migrates Midnight data, signs official releases, installs changes into Electron, or restores a broken app/plugin. Those are host responsibilities, not capabilities established by the cited Pi docs. [SDK](https://pi.dev/docs/latest/sdk), [Packages](https://pi.dev/docs/latest/packages)
- The distribution licenses and native requirements of arbitrary future third-party plugins cannot be established until their concrete dependency sets exist.

## What does Pi Durable actually guarantee, and how compatible is it with coding-agent Pi?

### Takeaway

Pi Durable is a distinct experimental harness for durable conversations, tasks and typed application state. It provides storage-first recovery and live named registry replacement, but it does not make arbitrary external effects exactly once and is not a drop-in replacement for coding-agent sessions/extensions. [Durable README](https://raw.githubusercontent.com/earendil-works/pi/v1.2.0/packages/durable/README.md), [Durable source](https://raw.githubusercontent.com/earendil-works/pi/v1.2.0/packages/durable/src/harness/tool.ts)

### Cited Findings

- Durable is published as `@earendil-works/pi-durable`, built on `@earendil-works/pi-ai` and `@earendil-works/chord`. The README explicitly calls it experimental and says API changes occur without notice between releases. The official launch distinguishes it from Pi coding-agent: a framework for agentic applications, not a replacement terminal agent. [Durable README](https://raw.githubusercontent.com/earendil-works/pi/v1.2.0/packages/durable/README.md), [Launch post, 2026-10-01](https://earendil.com/posts/pi-durable/)
- Durable provides memory, SQLite and JSONL storage, custom-storage conformance tools, per-conversation model/tool/instruction/cwd settings, forks, compaction and task ownership. One process owns storage; remote clients attach to that owner. A host supplies execution environments and networking. The launch describes Node execution and small custom adapters, including remote environments. [Launch post](https://earendil.com/posts/pi-durable/)
- Entries, task checkpoints and typed JSON documents can commit atomically. Only committed state is observable. External effects explicitly do **not** occur inside that storage transaction. Conversation/task ownership is attribution and cancellation structure, not an access-control capability. [Normative specification](https://raw.githubusercontent.com/earendil-works/pi/v1.2.0/packages/durable/docs/spec.md)
- On reopening storage, unfinished work remains available; `Harness.open(...)`, `harness.resume()`, `harness.root(...)`, `conversation.submit(...)` and submission `.wait(...)` implement the lifecycle. A repeated submission `requestId` returns the existing submission. This deduplicates admission, not all tool effects. Typed documents support initial/current/as-of fork values and document observation. [Durable README](https://raw.githubusercontent.com/earendil-works/pi/v1.2.0/packages/durable/README.md)
- A Durable extension is a named object of tools, sections, hooks, wrappers and tasks installed into an application-owned registry. `createRegistry()` includes built-in generation/tool/compaction tasks that cannot be replaced; `registry.install(extension)` atomically replaces an installed extension of the same name. Registry code is not persisted. [Registry source](https://raw.githubusercontent.com/earendil-works/pi/v1.2.0/packages/durable/src/harness/registry.ts)
- Running calls finish with their original code; later calls/phases resolve new registry code. Conversation records store extension/tool names. After restart, the application installs implementation code again. Missing/unmigratable task definitions block pending tasks until suitable definitions appear; reopen does not silently terminalize them. [Durable README](https://raw.githubusercontent.com/earendil-works/pi/v1.2.0/packages/durable/README.md), [Specification](https://raw.githubusercontent.com/earendil-works/pi/v1.2.0/packages/durable/docs/spec.md)
- Source-level replay contract: a tool's validated final arguments and replay policy are persisted before `execute()`. Default policy is unsafe. Recovery reruns only when both the persisted policy and currently installed tool declare `replay: "safe"`; otherwise it produces an interrupted result saying the call may have partially run. This source does not stop a model issuing a new call for the same semantic action. [v1.2.0 ToolTask source, lines 147–176](https://github.com/earendil-works/pi/blob/v1.2.0/packages/durable/src/harness/tool.ts#L147)
- Durable 1.2.0 adds nested `ToolExecutionApi.executeTool`, a Durable-specific codemode extension and tool-search module. Nested calls inherit validation, hooks and their own replay policies; stable nested keys reconnect replaying callers to existing calls. Codemode reconstructs deterministic execution from a journal; changed sandbox fingerprints/module versions, divergence or deadlines fail recovery. This is new released capability, not evidence of coding-agent extension compatibility. [Durable 1.2.0 changelog](https://raw.githubusercontent.com/earendil-works/pi/v1.2.0/packages/durable/CHANGELOG.md)
- 1.2.0 also changes tool result `content` to `output` with `structuredOutput` and changes storage-error handling to fail/close the Session; storage implementations must handle their own transient retries. The tag includes task migration changes. Adopting newer Durable requires a fresh API/storage/recovery assessment. [Durable changelog](https://raw.githubusercontent.com/earendil-works/pi/v1.2.0/packages/durable/CHANGELOG.md)
- Durable's Node SQLite adapter imports `DatabaseSync` from built-in `node:sqlite`. Its manifest requires Node >=22.19.0; its images use Photon WebAssembly with optional Node workers. This is not proof that every Electron package/build target works without qualification. [SQLite adapter](https://raw.githubusercontent.com/earendil-works/pi/v1.2.0/packages/durable/src/storage/sqlite/node.ts), [Manifest](https://raw.githubusercontent.com/earendil-works/pi/v1.2.0/packages/durable/package.json)
- Local evidence: Midnight ADR 0001 accepted coding-agent SDK 1.0.1 plus its SQLite action/mission journal. The recorded 2026-10-04 spike found that both runtimes let the model reissue a previously executed send; Durable's unsafe interrupted result and submission requestId did not prevent two effects. This is a repository-recorded test, not a fresh 1.2.0 measurement. [ADR 0001](../../docs/adr/0001-runtime.md)

### Inferences

- An interrupted nonreplayable deployment/send/install still needs reconciliation. A model can retry with a new call identity, so Midnight should retain semantic action identities, receipts and unknown-outcome handling outside the model's discretion, whatever harness it chooses. This follows directly from the boundary between storage commits and external effects, and local duplicate-send evidence. [Specification](https://raw.githubusercontent.com/earendil-works/pi/v1.2.0/packages/durable/docs/spec.md), [ADR 0001](../../docs/adr/0001-runtime.md)
- Durable live replacement does not imply safe activation of arbitrary generated code: persisted tasks may resume against changed code; imports, task/data migrations, dependency pinning, capability authority and health checks remain the host's job. [Registry source](https://raw.githubusercontent.com/earendil-works/pi/v1.2.0/packages/durable/src/harness/registry.ts), [Specification](https://raw.githubusercontent.com/earendil-works/pi/v1.2.0/packages/durable/docs/spec.md)
- An adapter is needed to reuse tools/resources between coding-agent and Durable: factories, execution signatures, result shapes, hooks, environment and session state differ. Both share Pi AI, but no direct coding-agent `ExtensionAPI` loader compatibility was established. [Coding-agent extensions](https://pi.dev/docs/latest/extensions), [Durable tool types](https://raw.githubusercontent.com/earendil-works/pi/v1.2.0/packages/durable/src/harness/types.ts)

### Gaps

- No fresh install or crash spike was performed against 1.2.0. The 1.0.1 ADR's missing/undocumented codemode/tool-search concern is partly outdated; its duplicate semantic-action concern remains a valid design risk. Re-run the host contract gates before any migration. [ADR 0001](../../docs/adr/0001-runtime.md), [1.2.0 changelog](https://raw.githubusercontent.com/earendil-works/pi/v1.2.0/packages/durable/CHANGELOG.md)
- No documented built-in authenticated network server, app permissions sandbox or official release/signing pipeline was established. `watch()` state transport and registry replacement are primitives to integrate, not full infrastructure. [Launch post](https://earendil.com/posts/pi-durable/), [Security](https://pi.dev/docs/latest/security)

## How should Midnight integrate a separate builder for local and shared changes?

### Takeaway

Keep the current serving runtime and journal while adding a dedicated Pi coding-agent builder session in an isolated worker. Use the SDK inside that worker for direct API access; RPC is a supported alternate process interface. Durable is a future evaluation candidate, not a prerequisite for self improvement. [SDK](https://pi.dev/docs/latest/sdk), [RPC](https://pi.dev/docs/latest/rpc), [ADR 0001](../../docs/adr/0001-runtime.md)

- Verified SDK building blocks in **both** v1.0.1 and v1.2.0: `createAgentSession({ cwd, tools, sessionManager })`; explicit built-in names such as `read`, `bash`, `edit`, `write`; `SessionManager.create(cwd, sessionDir)` for a new persistent session; `SessionManager.open(path)` for a specific persisted session. `SessionManager.continueRecent(cwd)` exists, but explicit session identity is preferable when multiple change requests share a directory. [1.0.1 tools example](https://raw.githubusercontent.com/earendil-works/pi/v1.0.1/packages/coding-agent/examples/sdk/05-tools.ts), [1.0.1 sessions example](https://raw.githubusercontent.com/earendil-works/pi/v1.0.1/packages/coding-agent/examples/sdk/11-sessions.ts), [1.2.0 sessions example](https://raw.githubusercontent.com/earendil-works/pi/v1.2.0/packages/coding-agent/examples/sdk/11-sessions.ts)
- Both tags show full host control through a `ResourceLoader`, `SettingsManager.inMemory(...)`, explicit `agentDir`, model/runtime, `session.subscribe(...)`, `session.prompt(...)` and `session.dispose()`. Resource loading can return empty extensions/skills/prompts/context files and a host-written system prompt. [1.0.1 full-control example](https://raw.githubusercontent.com/earendil-works/pi/v1.0.1/packages/coding-agent/examples/sdk/12-full-control.ts), [1.2.0 full-control example](https://raw.githubusercontent.com/earendil-works/pi/v1.2.0/packages/coding-agent/examples/sdk/12-full-control.ts)
- Current SDK also exposes `steer()`, `followUp()`, `abort()`, `waitForIdle()` and session events. `agent_settled` means the agent will not continue automatically; it does not mean tests or host success conditions passed. Default sessions use ambient resource/settings/credential discovery unless overridden. [SDK](https://pi.dev/docs/latest/sdk)
- Current Midnight already explicitly disables ambient extensions, skills, prompt templates, themes and context files, supplies the broker extension and custom tools, and binds extensions. Existing `tools` comes from host-supplied tool names; upstream's possession of coding tools does not mean Midnight currently gives those tools to its serving session. [Adapter](../../src/runtime/adapter.mjs)
- RPC runs a long-lived subprocess with JSONL stdin/stdout commands/events. Current exported `RpcClient` provides a typed client. The `prompt` response indicates acceptance/queueing/handling; completion requires the run event lifecycle. Framing/backpressure and stderr logging are host integration obligations. [RPC protocol](https://pi.dev/docs/latest/rpc)
- Coding-agent 1.2.0 is ESM and requires Node >=22.19.0. Native Windows CLI tool setup uses Git Bash by default, supports an optional PowerShell tool, or Linux Bash inside WSL. Tool availability and sandboxing must be qualified for the actual worker distribution. [Manifest](https://raw.githubusercontent.com/earendil-works/pi/v1.2.0/packages/coding-agent/package.json), [Windows guide](https://pi.dev/docs/latest/windows)

### Inferences

- Recommended integration sequence: Midnight creates a change request and prepared checkout/plugin workspace; a separate worker constructs an explicit builder `createAgentSession`; its `SessionManager` file and change-request ID live in Midnight's journal; host tools execute through the existing policy boundary against the isolated workspace; streamed events feed a build UI; host-controlled checks produce the candidate; a separate activation/release component applies the checked artifact. This is an architecture recommendation, not an upstream Pi product feature. [SDK](https://pi.dev/docs/latest/sdk), [Security](https://pi.dev/docs/latest/security), [ADR 0001](../../docs/adr/0001-runtime.md)
- Do not put source-repair shell powers into the ordinary serving session or import arbitrary generated plugins into Electron's main process. A Pi SDK inside a dedicated worker preserves API access and containment; a child process alone is crash containment and needs an OS boundary to constrain authority. [SDK](https://pi.dev/docs/latest/sdk), [Security](https://pi.dev/docs/latest/security)
- For personal installs, the builder can target a local plugin/overlay revision and preview before activation. For official improvements, target a source branch and reviewable release candidate. Keep bootstrap, updater, broker, journal/reconciliation and recovery UI small and stable so a broken plugin can be disabled independently. This is host architecture inferred from full host control and in-process extension permissions. [Full-control example](https://raw.githubusercontent.com/earendil-works/pi/v1.2.0/packages/coding-agent/examples/sdk/12-full-control.ts), [Security](https://pi.dev/docs/latest/security)
- Pin and qualify upstream 1.2.0 separately; current documentation is not a compatibility promise for 1.0.1. Durable can later implement the same runtime boundary if it passes policy, action reconciliation, migration, restart and UI contract gates. No wholesale engine migration is needed to create the initial builder. [ADR 0001](../../docs/adr/0001-runtime.md), [Durable changelog](https://raw.githubusercontent.com/earendil-works/pi/v1.2.0/packages/durable/CHANGELOG.md)

### Gaps

- This research verified API names against released tags but did not compile a builder or run Electron worker packaging, sandbox, reload, migration or crash tests. Exact method/options behavior must be checked against Midnight's vendored declarations when implementation begins.
- Successful generated plugin behavior, source repair quality and rollback reliability require Midnight acceptance fixtures; upstream API existence alone establishes none of those outcomes.
